## 1. 结论先说

这次不是继续给旧 Native 调间距，而是以固定 ELK 源码为研究参考，重新实现完整分层布局与正交布线流水线，
再将研究方案提取为独立、离线、可直接调用的 H08 静态模块。

截至最终签收，约定范围内的视觉、正确性、产品集成和 Windows 离线交付门禁均已通过：

- 用户接受 SOP015 `_5426_`/`_5404_` 独立树、EQ012 `_1471_`、11组机制场景，以及最后的 sop001/eq006/dp002 分层样本。
- 完整单元测试808/808；原47个完整节点case在原45000ms worker和严格校验下47/47、硬违规0。
- 真实Single/Compare、手动override隔离与Reset、SVG导出、异步取消/过期结果隔离、session恢复和离线包均有验证。

因此可以说：**在已声明的平面网表支持范围和本次验收语料上，达到约定的ELK可读性水平。**
不能扩展成“所有图都与ELK一样好”“全面实现ELK”或“所有质量指标都更好”。

验收时应用版本1.1.0、H08包0.3.0、基础IR契约1.1.0、profile1.0.0。
验收后用户明确要求将H08设为默认：已修改新会话、无参数provider选择和EDA启动入口；
Simple保留为显式选择和失败回退，旧session中显式保存的provider继续尊重。本次默认切换版本为1.1.1，
其新增验证结果单独记录，不将1.1.0的冻结哈希冒充新版本哈希。

## 2. 为什么前期写了很多，却没有达到效果

最初旧Native的问题不是单个树之间少几十像素，而是层次、排序、对齐和布线各阶段之间的模型不一致。
局部加空白或后置挪节点，无法恢复前面已经丢失的分支关系。

2026-09-24固定SOP015 Focused3/3基线（57节点、60边）：

| 指标 | ELK 0.11.1 | 当时旧Native |
| --- | ---: | ---: |
| 视觉列数 | 12 | 7 |
| 总路由长度 | 18654.75 | 41274 |
| 逻辑交叉 | 28 | 228 |
| 物理交叉 | 28 | 187 |

旧实现的逻辑交叉约为参考的8.14倍，增加96px子树间距没有改变这些全局问题。
这也是后来停止“修修补补”，转向完整源码审计和相位取证的直接原因。

需要承认的流程问题是：早期过多依赖局部改动和通过的硬约束，没有足够早地把整图可读性、相位因果、
同尺度视觉和真实UI异步路径放到同一条验收链中。后面的工作就是补上这条链，而不是用更多测试数量掩盖差图。

## 3. 重新调研了ELK的哪些机制

研究固定在 Eclipse ELK commit `28e5173243cab0cf4e2c9816c803bc0d5c47ab24`；
产品同输入视觉参考使用仓库内vendored elkjs0.11.1。两者用途不同，不混用默认值或坐标当作同一参考。

| 阶段 | 新实现的职责 | 为什么影响读图 |
| --- | --- | --- |
| P0规范输入 | canonical身份、测量、固定端口、输入快照 | 避免名称/数组顺序和身份混淆改变结果 |
| P1方向 | 有界加权环打断，并保留逻辑方向恢复信息 | 给后续层次化提供可处理的方向 |
| P2分层 | tight-tree/Network Simplex排名与可行性诊断 | 决定逻辑跨度和长边，不是最后挪节点能替代 |
| proper graph | 长边dummy、反向端口处理、hyperedge dummy合并 | 排序和布线必须看到一致的跨层结构 |
| P3排序 | 固定端口分配、双向扫层、约束解算、交叉计数、H08分组候选 | 保护分支顺序和树的连续性 |
| P4坐标 | 四方向Brandes–Köpf对齐与压紧、冲突处理 | 保留对齐块，而非逐个节点塞入空位 |
| P5布线 | boundary hyperedge、依赖/环处理、critical split、槽位、层宽投影 | 坐标与通道容量共同形成正交路线 |
| 恢复与提交 | 逻辑edge lineage恢复、物理wire、共享硬校验 | 保证分支不断、不错并，不把半成品交给UI |

独立树清楚并不来自一个“识别树然后分开摆”的单独技巧，而是这些阶段共同保留结构、顺序、对齐和布线空间。
H08没有复制旧Native相位，也没有用实例名或固定坐标特判SOP015。

## 4. 开发过程中的关键转折

### 4.1 从最终截图追到首个分歧

先冻结源输入、provider输入、选项和代码哈希，再沿P0→P5定位首个可解释差异。
采用固定Java oracle相位快照、同前置输入回放、完整几何差分、改名和排列测试。
“最后看起来变好”不能代替对拥有该行为的阶段作出解释。

### 4.2 多个单项修正失败，没有强行部署

- 显示名参与排序会造成仅改标签也改变布局，因此引入独立结构排序摘要；但早期单变量试验导致EQ分支质量退步，保留失败并回退。
- 每条逻辑边需要独立隐式端点身份，可修复长边链混合问题；但单独启用曾使EQ/clk物理路线明显膨胀，不能直接作为最终方案。
- 仅在原槽位内把成员聚拢，或只追求碎片为0，会增加交叉，多个候选被原交叉预算拒绝；没有放宽阈值硬过。
- 试验按预登记因素组合比较，不搜索备用seed、hash或fixture专用开关来挑好结果。

这些失败说明身份正确、分支连续和物理共享是不同问题，不能用其中一个指标代替另一个。

### 4.3 H08形成：逻辑身份独立，物理锚点可以共享

H08保留每条逻辑边/端口的canonical身份和lineage；在P5中，只对**同物理net、同节点、同侧、精确同局部锚点**
的端点建立额外scratch adjacency，让它们共享物理干线。不同net/节点/侧/点绝不合并。

P3使用拓扑派生的显式成员提示、结构排序键、固定候选数和unit-sweep；P3预测视觉band和P5最终层宽投影共用测量函数，
避免“原rank连续”却在完成图中被拆成多个视觉列。它不是collapse，也不是布局完成后重新挪树。

同前置取证证明H08物理锚点变化只发生在P5，而非隐藏改P0～P4、节点测量或随机种子。
这是一项明确记录的项目适配策略，不宣称它是ELK原样已有的功能，也不把它包装成ELK自身的bug修复。

历史同次H08质量报告中，SOP5426逻辑/物理交叉10/7、逻辑线长13854.167；
dp002被追踪reset边从早期50折降为4折，但全图最大仍为12折。其他图仍有逻辑交叉、长线、空白和隐藏标签代价，
不构成所有指标支配ELK的结论。具体数字属于对应冻结实验，不能与不同运行的参考拼成新对照。

### 4.4 全图超时确实阻塞了交付

保留了研究H08原47例43/47、后续44/47，以及首个完整静态版本46/47等失败；超时一律算失败。
没有增大45秒、缩图、启用折叠、删除case或放松validator。

按已记录的窄范围恢复授权，只处理门禁所需热点：P2内部身份/树状态、P5依赖身份、摘要分配、共享空间查询、
P1首成员查找和可证明恒零的P3计分等。每项保留旧实现差分，要求结果和运算语义不变。
实际DP020的完整P3捕获为41079节点、93556端口、46782边；诊断、正式未采样门禁和环境噪声分开记录。
其余性能工程没有因此自动重新开启。

最终正式产品快照47/47通过，但最大布局41897ms已接近45000ms门限，不能承诺持续稳定或所有机器都一样快。

### 4.5 从研究原型迁为真正的离线静态包

研究工具曾使用Node编译/注入来验证假设，这不能当浏览器交付。
随后把机制逐步提为唯一ES-module实现：研究入口改为复用静态函数，不保留两份算法。
静态迁移每批对六个产品图逐字段比较，并核对完成态SVG，避免“提取时顺手换了布局”。

现在可clone后直接调用，无npm install、bundler、C++动态库或在线服务要求：

```js
import {layoutGraph} from './src/layout/elk_native/h08.js';
const result = await layoutGraph(measuredGraph, {signal: abortController.signal});
```

调用方负责节点/端口测量；API输入是测量后的图，不是Verilog文本。结果只发布完整、已校验的不可变几何。
当前采用JavaScript原生ES modules，没有迁往C++；“clone即可调用”的需求通过静态模块解决。

### 4.6 产品接线发现了算法单测没有覆盖的问题

真实UI切换时发现调度器只将ELK ID当成异步，H08返回Promise后触发Simple回退；改为共享的provider异步能力声明。
session恢复又发现首张异步图尚为空时统计面板读取graph；改为Pending状态，并增加空图到完成图的执行型测试。
两项都修在共享边界，没有为Single/Compare复制算法或隐藏失败。

旧Native的22个源文件已移出src，保留在测试参考目录供历史追溯；架构测试禁止产品重新导入。
Windows包中不包含旧Native、研究编译器或测试参考树。

## 6. 当前限制与没有做的事

- 支持范围是声明过的平面网表、固定左右侧端口及验收语料，不是完整ELK选项集合。
- 分组forecast对grouped self-loop和merged rank columns仍有显式限制，不支持时诊断，不返回伪成功图。
- 同步相位只能在检查点响应取消，不保证浏览器主线程即时抢占；超大图仍优先Search-first/Focused。
- 线长、交叉、留白、标签可见性存在权衡；硬0不意味着每张未见图都好看。
- 超时和内存稳定性仍有风险，本轮通过不等于长期压力测试完成；其他性能项目继续暂停。
- 旧Native只在测试参考中保留，不是运行时隐藏fallback；失败fallback仍明确使用Simple。
- 本轮代码在`dev`工作树内，包含长期未提交改动；没有自动commit、push或对外发布。
